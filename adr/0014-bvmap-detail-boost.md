# ADR 0014: bvmapの印刷を深いズームのタイルで描く(詳細ブースト)、bvmap-darkをbvmap-starlightに置き換える

- ステータス: 採用・実装済み(2026-10-03、hfuさんの承認: A案・文字補正なし・starlight置換)
- 日付: 2026-10-03

## コンテキスト

hfuさんの現地調査(フィールドワーク)の結果、`bvmap`系スタイルで印刷すると
**建物などの表示が乏しく物足りない**、という指摘を受けた。

原因はデータ側にある(bvmapのTileJSONと`vector_layers`で確認):

- bvmapは4段階の縮尺帯でタイルが作られている(tippecanoeの生成オプション):
  z4–7(500万分の1)・z8–10(100万)・**z11–13(20万)**・**z14–16(2.5万)**。
  maxzoomは16。
- **建物`BldA`はz14以上のタイルにしか存在しない**(`minzoom: 14`)。道路縁
  `RdEdg`・水涯線`WL`などの細部はz16のみ。
- スタイル側の`BldA`レイヤーにはminzoomの制限が無い——z14以上のタイルを
  取れば、スタイルはそのまま建物を描く。
- つまりz12でもz13でもデータ密度は同じ20万分の1帯で、**建物はz14を取って
  初めて出る**。zukakuの詳細ページはピッカーの縮尺次第でz12前後になりうる
  (例: ピッカーz10・130pxセル → ページは約z12.6)ため、疎な印刷になっていた。

## 検討した手段(実測)

| 手段 | 結果 |
|---|---|
| ソースの`tileSize`を256/128にして深いタイルを取る | **不可**。maplibre-gl 6.6では、ベクタソースの`tileSize`が512未満だとスタイルの適用自体が始まらず無言でハングする(512は正常)。ロード後に書き換えても深いタイルは再取得されない |
| **`renderScale`(ADR 0009)で膨らませて縮小** | **可**。コンテナをk倍にすると`fitBounds`がlog2(k)段深いズームに着地し、その段のタイルを取る。z12ページでk=2→z13(タイル9→25枚、街路・町名は増えるが**建物は出ない**)、k=4→z14(80枚、建物・街区が出る) |
| stars側に印刷用のタイルセットを作る | 非採用。建物は約8000万フィーチャーあり、z11–13の帯に入れるとタイルが非現実的に重い |

## 決定

**bvmap系スタイル(当面`bvmap-starlight`のみ)の詳細ページに、概要ページが既に
使っている`renderScale`を自動で付ける**(詳細ブースト)。

- **対象**: 詳細ページのみ。概要ページは従来どおり(`renderScale:{x:cols,y:rows}`、
  ADR 0009)。概要は索引なので建物の密度を求めない。
- **ブースト量**: ページの素のズームz0(`fitBounds`が着地するズーム。
  A4相当のコンテナに`bbox`をpadding 0で収めた値)から、
  `k = min(4, 2^ceil(14 − z0))`。**kは2の冪**(ズームを整数段ずらす)にし、
  **小数のz0から計算する**——ベクタタイルは`floor(zoom)`で選ばれるため、
  例えばz11.9に+2段でも13.9となってz14帯に届かない。
- **上限k=4**(+2段): これ以上はz0が低すぎてもブーストしない/頭打ちにする
  (z0<12のページはz13止まりで、建物は出ないが街路・注記は増える)。
- **文字補正はしない**: スタイルがpxで描くもの(注記・アイコン)もk分の1に
  縮む。z12→z14(k=4)の実測で、注記の字高は約1mm(約3pt)。300dpi相当で
  印刷したときの5cm四方を確認し、街区・建物が1棟ずつ見え、注記も鮮明で
  あることを確認した。hfuさんが「許容できる」と判断。スタイルの`text-size`等を
  k倍するスタイル変換(補正)は、必要になったら別途検討する。
- **実装場所**: `docs/index.html`の`computePages()`(`detailBoost()`)。
  `computePages()`の返り値に`renderScale`を足すだけなので、
  `docs/requests/*.json`のスキーマ・`scripts/render/atlas-page.html`・
  `computeSheets()`はいずれも無変更(どちらも元々ページの`renderScale`を
  そのまま`AtlasSheet`に渡す)。ライブラリ(`@dwg7/maplibre-gl-atlas`)も無変更。

**スタイルの置き換え**: ピッカーの`bvmap-dark`を`bvmap-starlight`に置き換える
(hfuさんの指示)。stars上の両スタイルはレイヤー構成が同一(123層)で、
色とスプライトだけが違う。

- ピッカーのボタンと`STYLE_IDS`を差し替え。
- 共有URL(ADR 0011)の`style=bvmap-dark`は`bvmap-starlight`に読み替える
  (`restoreStateFromHash()`)。
- 既存の`docs/requests/*.json`が`bvmap-dark`を名指ししていても、starsが
  そのスタイルを配信し続ける限り、そのまま描画できる(`atlas-page.html`は
  JSONの`style`をそのままURLにする)。

## 実測で訂正した当初の見込み(記録)

当初「`renderScale`のキャンバスがMapLibre既定の`maxCanvasSize`(4096px)で
頭打ちになり、縮小後の実効解像度が約88dpiまで落ちる」と見込み、ライブラリで
上限を8192に上げる案を試した。**これは検証ハーネス側が縮小した数値を実際の
解像度と取り違えた誤りだった。** 実パイプラインは縮小**前**のキャンバス
全体をPDFに埋め込み、表示側で縮める。同じ請求(1×2グリッド、k=4)で比較:

| | PDFサイズ | 描画時間 | 詳細ページの埋め込み画像 |
|---|---|---|---|
| 上限4096(MapLibre既定) | **8.9MB** | 約20秒 | 2896×4096(約350dpi相当) |
| 上限8192 | 24.7MB | 約50秒 | 5792×8192(約700dpi相当) |

既定の上限4096でも十分な解像度があり、むしろファイルサイズと時間の
歯止めとして働く(PDFは`docs/responses/`にコミットされ、GitHubのファイル
サイズ上限もある)。**上限は変更しない**(ライブラリの変更は取り消した)。
一方、概要ページも同じ上限に当たっている(例: 3×3以上のグリッドで
縮小前のキャンバスが4096pxで頭打ち)が、実用上の解像度は保たれている。

## 影響・注意点

- **stars(共有の本番環境)への負荷**: ブーストしたページは1ページあたり
  約80タイル(z12ページは9枚)。10ページのアトラスで約800リクエスト。
  CLAUDE.md 4節のとおり共有環境であることを意識し、キャッシュ効果と
  あわせて様子を見る。
- **ブラウザ内印刷(Print in Browser)**: k=4のステージは3176×4492 CSS px
  (DPRが高いとさらに大きい)。MapLibreが4096pxに頭打ちにするため上限は
  守られるが、GPUメモリを多く使う。低スペックな端末では重くなりうる。
- **描画時間の見積もり表示**(`#page-estimate`)はブーストを織り込んでいない。
  ローカル実測ではブーストしたページでも1ページ数秒〜十数秒で、見積もりの
  桁は大きく外れない。
- `scripts/render/lib.js`の待機タイムアウトを1ページあたり20秒から30秒に延長
  (ブーストしたページはタイル数が多いため)。
- 概要ページ(z0相当のLOD)と詳細ページ(z14相当のLOD)でデータの詳しさが
  異なる。概要は索引としての用途なので許容する。
- ブーストの対象スタイルは`BOOST_STYLES`で明示する。`positron`(グローバルの
  OSM)・`std`(256pxラスタ)には適用しない——これらは別の設計で、
  同じ「縮尺帯ごとにデータが間引かれる」問題を持たない。
